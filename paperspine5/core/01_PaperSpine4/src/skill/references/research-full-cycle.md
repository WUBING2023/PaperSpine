# From a research topic to a paper

Use when new research or analysis is requested or selected under the saved scope.
For supplied-results writing, use [research.md](research.md)'s materials-only path;
for rewrite, review or a local figure correction, retain that request's scope.
The full-paper entry and standalone research stage use this method. Read each
linked method as needed, retaining the original inputs and revision history.

## The useful path at a glance

| Current dependency | Host decision and observable result | Reused methods |
| --- | --- | --- |
| Topic and permitted research | Choose a feasible question, inputs and bounded budget; identify what would answer it | [intake](intake.md), [research scope](research.md) |
| What is already known | Read close work and suitable venue papers; state what is established, disputed or still untested | [research](research.md), [citations](citation.md), [journal learning](journal-learning.md), [target research](target-journal-research.md) |
| A question worth executing | Specify a refutable hypothesis or descriptive purpose, unit of evidence, fair comparator and analysis before inspecting outcomes | [contribution](contribution.md), [results validation](results-validation.md) |
| Design feasibility | Execute a small pilot of the actual method and controls; retain failures and revise an infeasible design | The design and execution sections below |
| Evidence | Run the selected design on real inputs, preserve commands/code/results and inspect completeness | [Agent handoff](agent-orchestration.md), execution below |
| An answer within its limits | Analyze according to the design, retain contrary evidence, distinguish planned and exploratory findings | [results validation](results-validation.md), analysis below |
| Explanation and paper | Build scientific figures and a complete argument from the actual results; apply learned venue layout | [scientific figures](scientific-figure-workflow.md), [build](build.md), [manuscript format](manuscript-format.md) |
| Independent criticism and revision | Review current evidence, images and manuscript; repair affected sources and inspect the new version | [review policy](review-policy.md), [evidence review](evidence-grounded-review.md), [rewrite](rewrite.md) |

These dependencies can overlap: venue learning can run beside prior-work reading;
Methods and figure planning can begin during an experiment. A dependent conclusion
cannot precede its evidence. At each transition ask which user/paper outcome the
next action improves, what smaller honest action would answer the gap, and which
actual artifact will show it. No fixed number of experiments, roles or approvals
substitutes for answering the question.

## Resolve topic, question and limits

Read the request and saved configuration before choosing research. Identify the
intended audience, research purpose, data/source availability and allowed resource
use. A topic-only request has no missing prior manuscript: establish the generated
workspace and proposed sources in the same task. Use the conversation, or the
saved workbench configuration when selected. Record delegated topic and venue
choices as Agent choices. Do not invent consent, ethics, permission or author facts.

Convert a broad topic into a question whose answer fits the available evidence.
For an empirical comparison, specify the objects/population, intervention or
method, comparator, outcome and conditions. For a qualitative, theoretical or
descriptive study, specify the corpus/cases, interpretive or proof criteria and
what evidence could contradict the proposed account. Do not force an inferential
test onto a question it cannot answer. A replication or bounded exploratory study
can be useful without a novel algorithm or a publication claim.

Before expensive work, state a realistic ceiling for wall time, compute, storage,
concurrent jobs and paid services actually available. Reserve time for inspecting
results, figures, review and revision. A single CPU pilot may be the right first
experiment; do not prescribe it for every field. Private uploads, participant
contact, external publication and payments require their own authorization.
Continue safe local design while indispensable external facts remain unresolved.

## Read prior work to change the design

Use [journal-learning.md](journal-learning.md)'s saved distinct reading sets and
[citation.md](citation.md)'s identity and point-of-use checks. Search the precise
question, method/comparator names and competing explanations; keep actual search
terms, source identities and parts read in the existing literature notes. Check
the closest relevant paper's Methods, Results and figures before asserting a gap.
Distinguish retrieval/access failure from no relevant work, and bounded search
coverage from proof that no previous study exists. A known close comparison may
turn the project into replication or robustness exploration; retain that useful
purpose instead of manufacturing novelty.

Each pivotal reading should alter something concrete: the hypothesis, comparison,
measurement definition, failure case, design constraint, scientific figure or
interpretation. Record the source locator and the decision it informed. Abstracts
support only the points actually stated; they cannot establish detailed protocol,
figure or page-layout learning. Do not copy a published study's result into this
study or silently inherit its ethics/participants.

When a nearby result threatens the proposed contribution, search the phenomenon
as well as the method name: alternative terms, older formulations, and references
of the nearest papers can reveal the same problem in another algorithm family.
Read the relevant original passage, then compare what was already established,
what differs in this design, and what the saved evidence actually adds. An omitted
precedent may require changing the question rather than adding one citation.
For example, a prior demonstration that discrete scores and variable order change
selection rules out claiming that phenomenon as new; a saved diagnostic of
where a nested selection/tuning program changes can still answer a narrower
question. Similarity of topic alone does not prove that the newer study is redundant.

When stronger research is authorized, an acknowledged precedent should inform
the experiment, not only a weaker novelty sentence. Before expanding a grid,
identify the most consequential explanation the proposed result would still
leave open. Choose a feasible comparison whose possible outcomes distinguish
that explanation from the intended claim; use it in place of a redundant
scenario when the budget is fixed. A useful pilot checks this scientific
distinction as well as parsing and runtime. Record the expected differing
readouts in the existing design notes before inspecting the relevant outcomes.
An extra seed, rate or dataset helps only if it addresses the actual uncertainty.
After the contrast, revise the explanation from what it showed, including a null
or contrary result. A requested or well-motivated replication remains valid;
do not invent novelty or demand another experiment in materials-only writing.

For an open research topic, check the question before committing to its main
experiment. When a fresh scientific context is available and affordable, use
one brief independent formulation pass: give the original user problem, actual
closest-source passages, verified input availability and remaining budget, but
not the host's preferred plan or its defense. Ask for one executable alternative
that changes the estimand, key comparison or evidence source, and for the unknown
it could resolve that the closest work has not already answered. This is a
bounded proposal, not another reviewer vote or a novelty-score competition.
The host compares it with the current idea through the smallest real feasibility
check of their load-bearing input or identification assumption, then executes
one justified path. Do not eliminate a substantive hypothesis because a tiny
pilot happened to return a null. A different dataset, extra grid or renamed
method alone is not a different question. Retaining the original can be right
when its replication or decision use is concrete. Keep this choice and its
source evidence in existing notes, including an alternative that proved
infeasible; do not keep generating proposals until one sounds impressive.
If fresh context is unavailable, perform this reconsideration without claiming
independent input. This pass does not reopen supplied-results writing, a valid
saved contribution or an explicitly fixed user question, and does not authorize
switching the user's population, purpose or research scope.

For a named target, follow [target-journal-research.md](target-journal-research.md):
read current official article-type instructions and actual original local PDFs.
Inspect title/abstract, body, figures/tables and references. Keep submission rules
distinct from published reading design. Apply source-page observations to the
actual template and final rendered pages through manuscript-format.md; a venue
name, downloaded template or generic successful compile is not applied learning.

## Make the design executable before outcomes

Learn an unfamiliar step through a small worked example.

Identify the exact uncertainty first: a definition, comparator, estimator, control
or interpretive step. Read the relevant original method or a reliable teaching
source, including its assumptions and failure cases, rather than collecting a
general tutorial. Turn one lesson into an inspectable calculation or reasoning
example matched to this study; check an expected answer and a counterexample
before applying it to real evidence. Retain the source/page, adapted example,
actual check and resulting design decision in the existing research notes.
If the check fails, revisit the definition or implementation; successful retrieval
or a plausible explanation is not a validated application. Supplied-results
writing can perform this reasoning check without demanding new experiments.

For an empirical software study, Chang Xu's [research formulation and experiment
teaching](https://jyywiki.cn/ISER/2023/experiments.pdf), pp. 22–30 and 38–42,
is a useful example of turning a concept into a computable definition, showing
the precise difference from prior work, and separating manipulated, observed and
controlled factors. Transfer these decisions, not the course's study type or a
fixed experimental recipe, to the current question.

Worked example: suppose the uncertain concept is "ties affect top-k selection."
For scores `[5,4,4,1]`, k=2, there is one score strictly above the cutoff and two
at it; selecting one of those two permits two subsets. For `[5,4,4,1]`, k=3,
both tied items are included, so the repeated score permits only one subset.
Permutation-sensitive lexical priority and invariant semantic-ID priority can
now be checked on these inputs. This defines boundary ambiguity and disproves
the shortcut "any duplicate means selection must change". It is an adapted
teaching example, not empirical frequency evidence or a novel theorem. Apply
the verified definition to saved selections, then ask separately whether subset,
tuning and prediction changed; do not infer the downstream effect from ties alone.

Keep a compact, versioned design in the existing research notes or plan. State
the question and expected/refuting evidence, source identities and eligibility,
unit of observation, sampling or split, comparator conditions, primary outcomes,
analysis and the resource/stopping limits. Name important unavailable evidence.
The host resolves scientific tradeoffs and user-selected direction; workers can
propose changes but cannot quietly redefine the study after seeing results.

Operationalize a decisive criterion before outcomes. If a hypothesis fails when
a difference is "too small" or a loss is "acceptable", specify its justified
measurement and decision rule, or explicitly keep the study descriptive when
no meaningful threshold is available. A missing threshold discovered afterward
limits the hypothesis judgment; do not choose one from the observed results or
turn a tiny favorable sign into demonstrated support.

For computational comparisons, retain dataset/source version, splits, seeds,
preprocessing, tuning budget, stopping rules, metric definitions and hardware.
Use a credible simple baseline and the closest feasible comparator that answers
the question, not a deliberately weak opponent. Keep evaluation sets, input
availability, tuning/search budget and resources comparable; fit transforms and
choose hyperparameters using only the allowed training/validation information.
Report mismatches rather than concealing them. Existing user results remain
authoritative in a supplied-results request; these new-run requirements do not
retroactively require reproducing them.

When extending or replicating an existing study, inspect its producing code as
well as its prose before freezing the new comparison. Score transformations,
rank-tie and selection-tie rules, and invalid-value handling are part of the
method definition; the same method name does not establish equivalence. Preserve
the implemented definition for a replication, or identify a deliberate change
and its comparison consequences before examining new outcomes. Retain the prior
code and results rather than silently rewriting their meaning.

For other empirical work, apply the same comparability logic to exposure, case
selection, instruments, controls, timing and observation conditions. Correlated
measurements, repeated trials or multiple rows are not automatically independent
replicates. Define the relevant unit before selecting an uncertainty method.
For qualitative/theoretical work, retain corpus selection or assumptions and
compare plausible alternative interpretations or counterexamples. Do not add
randomization, causal claims or power that the design lacks.

Check what would change the conclusion if a competitor, selection rule or metric
were altered. Choose a small useful robustness check only when authorized and
affordable; do not build a universal benchmark suite. Fix the design before the
main outcomes. Later deviations stay visible with reason and version, and any
result-driven extension is labeled exploratory. Do not call a local plan a public
preregistration unless one actually occurred.

## Pilot, execute and retain failures

Run the smallest real pilot that tests the fragile dependency: input parsing,
split integrity, comparator feasibility, actual computation, measurement units
and rough resource use. It is not a synthetic success receipt. If a pilot informs
tuning or design, keep it separate from the later evaluation and retain that
change. Use constructed data only when it is an explicitly defined scientific
condition or demonstration; label its construction and never present it as
collected observations or replace a failed real input with unmarked simulated data.

Execute the chosen design, using [agent-orchestration.md](agent-orchestration.md)
when authorized workers/runtime are available. Preserve producing code, exact
commands/configuration, software/data versions, seeds where applicable, raw or
minimally transformed results and diagnostics. Keep them in the same workspace
with locators from reported quantities to source runs. Avoid output paths that
overwrite source data or the previous successful revision.

Inspect actual output, not only process exit: are expected comparisons present,
units correct, records complete, errors and non-finite values explained, and
measured resources within budget? Execution success means the computation ran;
it does not demonstrate the hypothesis. Keep failed runs, omissions and their
effect on interpretation. Repair a concrete defect with a bounded retry. After
two unchanged attempts, change the tactic, narrow the question or stop that
dependency; do not keep regenerating receipts, enlarging machinery or seeking a
favorable outcome. Preserve supported independent work.

## Analyze what was actually obtained

Apply the planned analysis to real results. Check denominators, units, ordering,
pairing, missingness and independence; retain transformations and source locators.
Choose uncertainty or tests only when the design, sample and question justify
them. Report effect/magnitude with meaningful uncertainty where available; do not
invent p-values, intervals or certainty for aggregates that do not support them.
If no inferential analysis was authorized or appropriate, a descriptive answer is
valid. Do not tune comparisons, seeds or exclusions to produce significance.

Compare the outcome with both the hypothesis and plausible alternatives. A larger
metric does not establish its causal source; an interval spanning no difference
does not prove equivalence. Negative, unstable, underpowered or incomplete results
may answer a narrower question. State whether each main claim is supported,
contradicted or unresolved, and the conditions that determine that judgment.
Mark newly motivated analyses as exploratory instead of rewriting their origin.
Use [results-validation.md](results-validation.md) in actual Results prose, not as
a requirement to manufacture a legacy table or gate.

## Turn evidence into scientific explanation and a complete paper

Plan useful result families and the question each figure answers before choosing
chart primitives. Follow [scientific-figure-workflow.md](scientific-figure-workflow.md)
and its original scientific mapping/story methods. Actually inspect suitable
reference figures; their visual structure transfers only when the present data
and interpretation still perform that scientific job. Figure, source numbers,
caption and Results must agree, with editable native labels, relationships and
data marks and an actual placed-size pixel check.

A method architecture explains the actual representation, transformations,
connections and evaluation conditions; ground these in implemented methods/code.
A mechanism explains supported processes and distinguishes observed evidence,
literature and hypotheses. A row of workflow boxes, generated component atlas or
statistical dashboard cannot stand in for that explanation. Reuse the existing
figure workflow's concept-generation/native component rules where applicable;
an honest architecture is not renamed a tested biological mechanism.

Use [build.md](build.md), [editorial-completeness.md](editorial-completeness.md) and
[assertive-scientific-writing.md](assertive-scientific-writing.md) to develop the
question, methods, findings and interpretation into the requested full manuscript.
Draft Methods during execution, but write result claims only from obtained
evidence. Reconcile title, abstract, contribution, Results and conclusion after
negative or narrowing findings. Do not pad the paper with file checks or imply
the study achieved the venue's novelty threshold.

Use one semantic manuscript and [manuscript-format.md](manuscript-format.md) for
requested PDF/DOCX/editable sources. Inspect every PDF page and the real DOCX or
faithful Word rendering, including figure placement, scientific text, citations,
tables, spacing and learned venue design. Submission and reading surfaces can
differ for a documented purpose, with the same scientific content. A conversion
log or PDF screenshots reused as Word proof is not dual-format visual acceptance.

## Independent review, affected revision and delivery

Arrange a separate-context reviewer using [review-policy.md](review-policy.md)
and [evidence-grounded-review.md](evidence-grounded-review.md). Supply the current
manuscript, real results/methods, sources, figures and renders with their locators;
do not supply an expected verdict or insist on an objection. Review scientific
design/comparability, evidence and alternative explanations as well as literature
use, explanatory figure value, editorial coherence and actual target layout.
The host/writer's self-check and a worker's result JSON cannot be called independent
review. Review availability and any evidence it could not inspect remain explicit.

For each located issue, decide the smallest scientifically valid repair: code or
analysis correction within scope, narrower claim, caption/figure change, source
format repair, or a justified response. New data collection, experiments outside
scope or target changes retain their user decision boundary. Keep the previous
revision; regenerate and review only outputs and downstream claims affected by
the change. A legitimate reviewer can find no actionable issue; never manufacture
one or claim review of an artifact that was not inspected.

Deliver the actual requested local paper and editable work package, with results,
necessary code/dependencies and concise unresolved limitations. Exclude private
inputs and copyrighted reference PDFs from sharing by default. Separate observed
product execution, scientific strength/novelty, independent review scope, venue
format and submission readiness. Unknown author/ethics facts or incomplete review
do not erase usable local work, and local delivery does not authorize submission.

For reproducible delivery, distinguish rebuilding the manuscript, recomputing
reported quantities from saved evidence, and rerunning the experiment. Give the
next researcher an entry command from the package root, required versions and
input provenance/licensing, and identify the expected output that tests each
promised operation. Reuse existing scripts; remove or parameterize accidental
dependencies on a private absolute path or a particular runtime attempt directory.
Test the promised operation from a separate extracted copy when feasible, retaining
the original results. A same-machine rebuild demonstrates that scope, not a clean
machine replication. Keep large arrays and unknown author/deposit facts explicit;
local packaging never authorizes uploading data, logs or copyrighted source PDFs.
